# Tech Design: 电子粉馆（/fenguan/）

## 1. 背景与目标
在博客里加一个轻量互动彩蛋页——「粉馆」，玩法参考 [A Dark Room](https://adarkroom.doublespeakgames.com/)：极简文字/字符画界面，靠点击驱动一个小型状态机（资源、属性、日志），营造"经营一家街边米粉馆"的沉浸感。

**目标**
- 访客能在一个页面里完成 点单 / 嗦粉 / 留言 三种核心动作，每次动作有文字反馈。
- 视觉上延续站点主题（minimal-black），Header/Footer 不变，只有 Body 是新玩法。
- 工作量可控——这是个"轻"彩蛋，不是新产品线。

**非目标（Non-goals，v1 不做）**
- 不做真正的多人实时同步（比如"当前有几位客人在馆里"这种跨访客共享的实时状态）——v1 只做自己的操作日志，但状态/日志的产生方式要留出扩展点，方便以后接后端做成真共享（见 §5「扩展点」）。
- 不做留言墙的实际存储/展示——v1 只放一个「留言」占位按钮，点了之后是"敬请期待"，不接入任何后端或 giscus（见 §6）。
- 不做账号系统、不做真实支付/订单。
- 不追求跨设备/跨浏览器状态同步（已确认接受纯本地、换浏览器重置）。

## 2. 现状与约束（决定技术方案的关键事实）
- 站点是 Hugo 静态站，`theme = "minimal-black"`，主题以 **git submodule** 引入（`themes/minimal-black`），不应直接改动主题源码，站点自己的 `layouts/`、`assets/css/pages/`、`static/js/` 是项目级覆盖/新增的位置（现有 `layouts/blog/*`、`content/uses.md` 就是这个模式）。
- Header 导航完全由 `hugo.toml` 的 `[[menu.main]]` 驱动，`header.html` 只是遍历渲染，**加入口不需要改模板**，只需加一条 menu 配置。
- 主题通过 CSS 变量 `--color-bg / --color-surface / --color-text / --color-text-muted / --color-border / --color-accent` 支持亮/暗色（`<html data-theme="dark|light">`），任何新页面要接入这套变量才能跟随全站主题切换。
- 现有 JS（`main.js`）的写法是无依赖 IIFE + `localStorage`（`try/catch` 包裹，防止隐私模式报错），新功能应延续这个风格，不引入框架。
- 站点目前唯一的"跨访客共享持久化"能力是 **giscus**（`layouts/partials/giscus.html`，基于 GitHub Discussions），用于博客评论。这是唯一现成的、免费、零维护的"后端"。

## 3. 入口设计
在 `hugo.toml` 的 `[menu]` 里，"装备"（weight 4）后面加一项：

```toml
[[menu.main]]
  name = "粉馆"
  pageRef = "fenguan"
  url = "/fenguan/"
  weight = 5
```

不改 `header.html`，桌面/移动导航都会自动带上新入口。

## 4. 页面结构与渲染方案
- 新增 `content/fenguan.md`，front matter 指定专属 layout（如 `layout: "fenguan"`）。
- 新增 `layouts/_default/fenguan.html`（项目级覆盖，参考 `about.html` 的接入方式，但内容自定义，不复用 `single.html` 的文章排版）。
- 新增 `assets/css/pages/fenguan.css`（复用主题 CSS 变量，保证亮/暗色一致）。
- 新增 `static/js/fenguan.js`（状态机 + 渲染 + `localStorage` 持久化，风格对齐 `main.js`）。
- 新增 `data/fenguan/menu.yaml`（Hugo data 文件，见 §6「菜单配置」），`fenguan.html` 渲染时把它序列化成一段内嵌 `<script type="application/json">` 交给 `fenguan.js` 读取——改菜单只改这个 yaml，不用碰 JS/HTML。

页面 Body 结构：

```
┌───────────────┬───────────────┬──────────────┐
│ 左：实时日志    │ 中：菜单（上）  │  右：属性/状态  │
│ （最近事件流）  │    动作（下）  │ （饱腹值/心情/  │
│                │                │  来访次数…）    │
├───────────────┴───────────────┴──────────────┤
│                留言（集中展示）                 │
└─────────────────────────────────────────────┘
```

移动端堆叠顺序：**日志 → 菜单/动作 → 属性/状态 → 留言（占位）**。

> v2 已移除顶部 ASCII 字符画（占地太大，参考 §12），日志紧跟在页面顶部之后，优先级仍高于属性/状态——这也和 §5 的扩展点一致：日志将来是要接跨访客数据的地方，值得放在更显眼的位置。

## 5. 状态设计（localStorage）
由于是纯静态站点，所有游戏状态默认是 **单浏览器本地** 的（换设备/清缓存即重置），这点需要和你确认是否可接受（见待确认问题 #3）。

```js
// key: "fenguan_state_v1"（内部 version 字段升到 2，见 §12——旧版本数据直接判过期、重置为默认值）
{
  version: 2,
  visits: 0,          // 累计访问次数
  satiety: 100,       // 饱腹值 0-100，第一次来访默认满值
  mood: 60,           // 心情 0-100
  bowl: null,         // 手里还没嗦完的一碗粉：{ itemId, name, remaining } | null
  ordersCount: 0,
  slurpCount: 0,
  log: [],             // 最近 N 条事件描述，环形缓冲（v2 起最多 20 条，日志框高度按 20 条估算，基本都能看到，见 §12）
  lastVisit: "2026-09-03T00:00:00Z"
}
```

### 扩展点：日志产出要为未来的"跨访客"留口子
v1 确认只做自己的操作日志，但你要求预留以后接共享数据的能力。做法是**不要在点单/嗦粉的按钮回调里直接 `state.log.push(...)`**，而是统一走一个小的事件记录函数：

```js
function recordEvent(type, text) {
  appendLocalLog(text);      // v1：写本地 log 数组，立刻渲染
  // 未来如果接了后端，这里加一行 postToBackend(type, text) 即可，
  // 调用点（点单/嗦粉的处理逻辑）完全不用改
}
```

这样以后要做"其他访客也在…"，只需要在 `recordEvent` 里加一次上报、在渲染时把本地日志和拉取回来的共享日志合并展示，不需要重构点单/嗦粉的业务逻辑。**这次不实现上报和拉取，只保证这一层抽象存在。**

## 6. 行为设计

### 点单（v2 已移除粉票，见 §12）
- 菜单配置化：`data/fenguan/menu.yaml` 里每个米粉品类是一条记录：`name`（品类名）、`mood`（点单时的心情增量）、`flavorTexts`（一组随机上桌文案）。改菜单/文案只改这个 yaml。
- v1 的具体品类和文案由 AI 先占位生成（比如牛肉粉/酸辣粉/螺丝粉/桂林米粉…配对应文案），最终基调你确认后再迭代，不阻塞开发。
- 点单不再检查/消耗任何货币，唯一门槛是饱腹值：饱腹值 ≥ 95（还很饱）时点单按钮点击后不产生订单，而是通过 `recordEvent()` 把"你还不饿，先逛逛再嗦粉吧"追加进日志框（而不是动作区的提示行），和其他事件文案保持一致的展示位置。
- 饱腹值 < 95 时可以点单：点击菜单按钮后，按钮内出现一个 2 秒的动态进度填充特效（模拟"上桌中"，同时防连点），填满后获得"一碗米粉"（写入 `state.bowl`，可嗦 3 次），并通过 `recordEvent()` 追加一条随机上桌文案到日志。再次点单会直接替换手里的碗（哪怕上一碗还没嗦完）。

### 嗦粉
- 前提是手里有碗（`state.bowl.remaining > 0`），没有则提示"碗已经空了，先点一碗新的粉吧"。
- 每次嗦粉：`bowl.remaining -1`、饱腹值 `+10`（上限 100）、心情 `+4`，日志追加一条随机趣味描述；`remaining` 减到 0 时碗清空（`state.bowl = null`）。
- 饱腹值同时会随停留时间自然衰减（每 10 秒 -1，见 §12），所以嗦粉本质是"跑得比饿得快"，需要不停点单/嗦粉才能一直维持高饱腹值。
- 冷却 1 秒（防连点），和点单按钮一样用按钮内的动态进度填充特效展示冷却进度，而不是单纯 disable。

### 留言（v1 只做占位，不接后端）
你确认这次先只放按钮，不实现存储/展示，把精力放在点单/嗦粉上。v1 做法：
- 一个「留言」按钮，点击后弹出/展示一行"敬请期待"提示，不产生任何网络请求或本地存储。
- 按钮要明确带"未开放"的视觉标记（比如置灰或加一个小徽标），不要让访客以为点了没反应是 bug。
- 真正的存储/展示方案留在下面的 Backlog，等这次的核心玩法跑通、你想做的时候再拉出来单独评审。

## 7. ASCII 美术（v2 已移除，见 §12）
v1 曾在页面顶部放一版简化的字符画占位（巷子轮廓 + 招牌 + 桌子），跑通交互后发现"轻量彩蛋"里这块字符画占屏幕比例过大，v2 已整块移除，页面直接从三栏布局开始。如果之后想找回视觉氛围，优先考虑更轻量的方式（比如小图标/emoji 点缀，而不是大段 `<pre>` 字符画），并留意窄屏换行和屏幕阅读器可访问性（`aria-hidden` + 文字摘要）。

## 8. 实施步骤（建议顺序，v1 范围）
1. 菜单入口 + 空页面骨架（S）
2. 三栏静态布局 + 小巷子 ASCII 占位 + 主题变量适配（M）
3. `data/fenguan/menu.yaml` 菜单配置 + AI 占位文案/品类（S）
4. 状态机 + `localStorage` 持久化 + `recordEvent()` 抽象 + 点单/嗦粉交互（M）
5. 留言占位按钮（"敬请期待"）（XS）
6. 移动端适配（日志优先于属性/状态）+ a11y 检查 + 文案/美术打磨（S）

## 9. 风险
- 文案和字符画的工作量容易被低估——"轻量"很容易在细节打磨阶段变重，尤其 AI 占位内容和你想要的"小巷子烟火气"基调可能需要几轮迭代才能对上。
- 留言按钮只是占位，如果视觉上不做"未开放"标记，容易被当成 bug。
- `recordEvent()` 的抽象是给未来扩展留的口子，v1 阶段不要过度设计（比如不需要真的定义好后端协议），够用即可，等真做共享功能时再具体化。

## 10. 决策记录（原待确认问题，已回复）
1. **实时信息展示**：v1 只做自己的操作日志，但通过 `recordEvent()` 抽象预留跨访客扩展能力（§5）。
2. **留言墙**：v1 只做占位按钮，不接 giscus 或任何后端；giscus 方案作为 Backlog 保留，等你想做的时候再启动。
3. **状态持久化范围**：接受纯本地 `localStorage`，换浏览器/清缓存即重置。
4. **菜单内容**：走配置化（`data/fenguan/menu.yaml`），v1 具体品类/文案由 AI 先占位生成，基调后续你再定调迭代。
5. **ASCII 美术方向**：街边小巷子里的粉馆，市井烟火气，先出简化占位版本。

## 11. Backlog（本次不做，先记录候选方案）
### 留言墙的最终形态
| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A. 复用 giscus** | 新开一个 GitHub Discussions category（如"粉馆留言"），`mapping="specific"` 固定 term，嵌入方式和现有评论一致 | 零新基建、零维护成本，和站点现有评论体系风格统一 | 留言需要 GitHub 登录；iframe 默认样式，很难做出"留言墙"的沉浸感 |
| B. 引入轻量第三方后端 | 如 Cloudflare Worker + KV，或直接用 GitHub Discussions GraphQL API 拉取展示、但走自定义 UI 提交 | 体验完全可控，能做出真正的"墙" | 需要新服务/API key/一点运维，不再"轻量" |
| C. 纯本地留言 | 只存 `localStorage`，仅自己可见 | 最省事 | 违背"集中展示给别人看"的诉求，不推荐 |

推荐顺序仍是 A → B：A 现有基建直接复用成本最低，B 留给"A 的沉浸感不够"时再上。

### 跨访客共享的实时信息
如果以后想做"当前有 N 位客人""刚刚有人点了 xx"，需要一个能接收/广播事件的最小后端（同样可以先复用 giscus 的 Discussion 作为极简事件源，或者上一个小型 KV 服务）。届时 `recordEvent()` 这一层抽象已经存在，改动集中在这一个函数和渲染合并逻辑，不涉及点单/嗦粉的业务代码。

## 12. v2 变更记录（v1 跑通后的调整）

v1 交互跑通后做了三处调整，核心动机是"字符画占地太大" + "粉票这层货币没必要，饱腹值本身就够驱动玩法了"：

1. **移除顶部 ASCII 字符画**：详见 §7，页面直接从三栏布局（日志/菜单+动作/属性状态）开始，不再有门头场景占位。
2. **饱食度 → 饱腹值，逻辑重做**（详见 §5、§6）：
   - 首次访问默认 100（满分 100），不再是 v1 的 60。
   - 只要页面开着，每 10 秒自然衰减 1 点，模拟"待久了会饿"。
   - 饱腹值 ≥ 95 时视为"还不饿"，点单会被拦截并提示"你还不饿，先逛逛再嗦粉吧"。
   - 一碗粉可嗦 3 次，每次嗦粉固定 +10 饱腹值（封顶 100），不再像 v1 那样嗦粉反而扣饱食度。
3. **移除粉票**：点单不再检查/扣除任何货币。新流程是"饱腹值 < 95 才能点单 → 点击菜单按钮触发 2 秒动态进度填充特效（同时防连点）→ 特效结束获得一碗米粉 → 才能嗦粉"。`menu.yaml` 里原本的 `cost`/`hunger` 字段随之去掉，只保留 `mood`（点单时的心情增量）和 `flavorTexts`。
4. **日志条数上限调整为 20，日志框高度同步加高**：环形缓冲最多保留 20 条；`.fenguan-log-wrap` 高度从 `20rem` 加高（当前 `30rem`，按实际卡片布局手调过，不必和内容实测高度完全对齐——反正整框都盖了渐变蒙版，见第 7 条），让更多条目能露出来，而不是像 v2 初版那样固定高度只够露出约 8-10 条。
5. **嗦粉按钮补上和点单一致的冷却体验**：冷却时长定为 1 秒，且不再是单纯 disable，而是复用同一套按钮内动态进度填充特效（`.fenguan-btn-fill`），视觉上和点单按钮的"上桌中"特效保持一致。
6. **日志框改为固定高度、禁止滚动**：`.fenguan-log-wrap` 用固定 `height`（见第 4 条）+ `overflow: hidden` 包住 `<ul class="fenguan-log">`，不再出现滚动条。
7. **日志淡出效果参考 A Dark Room 的 `notifications.js`/`notifyGradient`**：对照它的源码后发现它的做法比"手动给最后 N 条改文字颜色"更简单也更好看——
   - 它的日志列表是固定高度 + `overflow: hidden`，新消息 `prependTo` 到最前面，用 `opacity 0 → 1` 的 500ms 过渡淡入。
   - 视觉上的"旧日志变淡"完全不是靠 JS 给某几条元素改颜色，而是在整个列表上盖一层绝对定位的渐变蒙版（`#notifyGradient`：`linear-gradient(transparent → 背景色)`），越接近底部的内容越被蒙版盖成背景色，形成连续的淡出，而不是生硬的两级色阶；蒙版下方彻底看不见的元素再由一个 `clearHidden()` 定期从 DOM 里删掉（纯粹是性能清理，不是视觉效果本身）。
   - 粉馆按同样思路实现：`.fenguan-log-fade` 是叠在 `.fenguan-log-wrap` **整个高度**上的渐变蒙版（`inset: 0` + `linear-gradient(to bottom, transparent, var(--color-surface))`，用卡片自己的背景色变量，亮/暗主题自动适配），取代了之前"最后 2 条设置 `--color-text-muted`"的写法。**注意**：蒙版一开始做成了只贴在底部的固定 `6rem` 一条带（`bottom:0; height:6rem`），结果只有最后一两行落在渐变范围内、上面全部条目都是完全不透明——这不是"渐变"，只是"底部裁切"。改成 `inset:0` 覆盖整个日志框后，从第 1 条到最后一条才是连续、逐渐变淡的效果，跟 ADR 的 `#notifyGradient` 一样是铺满整个容器高度的。`renderLog()` 只在首次进页面铺历史日志（不带动画），后续每条新日志改由 `appendLogEntry()` 单独插入并做 500ms 淡入，而不是整份重画列表，同时把超出 `LOG_LIMIT`（20）的旧 `<li>` 直接从 DOM 里移除。

因为 state 结构变化较大（去掉 `tickets`，新增 `bowl`，`hunger` 改名 `satiety`），`localStorage` 里的 `version` 字段从 1 升到 2，旧数据会被当成过期版本直接重置为 v2 默认值——这是本站一直用的"版本不匹配就重置"策略，不做迁移。

## 13. 天气驱动的 subtitle（v2 新增）

给 subtitle 加了"结合实时天气描述粉馆氛围"的能力，动态替换 `content/fenguan.md` 里写死的默认文案，但不提具体地名（文案只是巷子/天气的氛围描述）。

**为什么这么做**：站点是纯静态 Hugo 站（GitHub Pages 托管），没有服务端、没有构建期定时任务，"实时"只能靠浏览器端直接发请求；引入任何需要 API key 的天气服务，key 都会明文暴露在前端 JS 里，不符合本站"零后端、零密钥"的现状（§2）。

**方案**：
- 数据源用 [Open-Meteo](https://open-meteo.com/)：免费、不需要注册/API key、原生支持 CORS，请求地址固定写死一组经纬度（不做浏览器地理定位，不弹权限请求，也不暴露访客真实位置）：
  ```
  https://api.open-meteo.com/v1/forecast
    ?latitude=29.03&longitude=111.70
    &current=temperature_2m,weather_code&timezone=Asia%2FShanghai
  ```
- `static/js/fenguan.js` 新增一整块独立逻辑（`WEATHER_*` 常量 + `weatherCodeToCategory`/`buildWeatherSubtitle`/`initWeatherSubtitle` 等函数），和点单/嗦粉状态机完全解耦：

# Tech Design: 电子粉馆（/fenguan/）

## 1. 背景与目标
在博客里加一个轻量互动彩蛋页——「粉馆」，玩法参考 [A Dark Room](https://adarkroom.doublespeakgames.com/)：极简文字/字符画界面，靠点击驱动一个小型状态机（资源、属性、日志），营造"经营一家街边米粉馆"的沉浸感。

**目标**
- 访客能在一个页面里完成 点单 / 嗦粉 / 留言 三种核心动作，每次动作有文字反馈。
- 视觉上延续站点主题（minimal-black），Header/Footer 不变，只有 Body 是新玩法。
- 工作量可控——这是个"轻"彩蛋，不是新产品线。

**非目标（Non-goals，v1 不做）**
- 不做真正的多人实时同步（比如"当前有几位客人在馆里"这种跨访客共享的实时状态）——v1 只做自己的操作日志，但状态/日志的产生方式要留出扩展点，方便以后接后端做成真共享（见 §5「扩展点」）。
- 不做留言墙的实际存储/展示——v1 只放一个「留言」占位按钮，点了之后是"敬请期待"，不接入任何后端或 giscus（见 §6）。
- 不做账号系统、不做真实支付/订单。
- 不追求跨设备/跨浏览器状态同步（已确认接受纯本地、换浏览器重置）。

## 2. 现状与约束（决定技术方案的关键事实）
- 站点是 Hugo 静态站，`theme = "minimal-black"`，主题以 **git submodule** 引入（`themes/minimal-black`），不应直接改动主题源码，站点自己的 `layouts/`、`assets/css/pages/`、`static/js/` 是项目级覆盖/新增的位置（现有 `layouts/blog/*`、`content/uses.md` 就是这个模式）。
- Header 导航完全由 `hugo.toml` 的 `[[menu.main]]` 驱动，`header.html` 只是遍历渲染，**加入口不需要改模板**，只需加一条 menu 配置。
- 主题通过 CSS 变量 `--color-bg / --color-surface / --color-text / --color-text-muted / --color-border / --color-accent` 支持亮/暗色（`<html data-theme="dark|light">`），任何新页面要接入这套变量才能跟随全站主题切换。
- 现有 JS（`main.js`）的写法是无依赖 IIFE + `localStorage`（`try/catch` 包裹，防止隐私模式报错），新功能应延续这个风格，不引入框架。
- 站点目前唯一的"跨访客共享持久化"能力是 **giscus**（`layouts/partials/giscus.html`，基于 GitHub Discussions），用于博客评论。这是唯一现成的、免费、零维护的"后端"。

## 3. 入口设计
在 `hugo.toml` 的 `[menu]` 里，"装备"（weight 4）后面加一项：

```toml
[[menu.main]]
  name = "粉馆"
  pageRef = "fenguan"
  url = "/fenguan/"
  weight = 5
```

不改 `header.html`，桌面/移动导航都会自动带上新入口。

## 4. 页面结构与渲染方案
- 新增 `content/fenguan.md`，front matter 指定专属 layout（如 `layout: "fenguan"`）。
- 新增 `layouts/_default/fenguan.html`（项目级覆盖，参考 `about.html` 的接入方式，但内容自定义，不复用 `single.html` 的文章排版）。
- 新增 `assets/css/pages/fenguan.css`（复用主题 CSS 变量，保证亮/暗色一致）。
- 新增 `static/js/fenguan.js`（状态机 + 渲染 + `localStorage` 持久化，风格对齐 `main.js`）。
- 新增 `data/fenguan/menu.yaml`（Hugo data 文件，见 §6「菜单配置」），`fenguan.html` 渲染时把它序列化成一段内嵌 `<script type="application/json">` 交给 `fenguan.js` 读取——改菜单只改这个 yaml，不用碰 JS/HTML。

页面 Body 结构（对应你给的 UI 设计）：

```
┌─────────────────────────────────────────────┐
│           ASCII 字符画：街边粉馆门头            │  <- 顶部，静态字符画
├───────────────┬───────────────┬──────────────┤
│ 左：实时日志    │ 中：菜单（上）  │  右：属性/状态  │
│ （最近事件流）  │    动作（下）  │ （饱食度/心情/  │
│                │                │  粉票余额…）    │
├───────────────┴───────────────┴──────────────┤
│                留言（集中展示）                 │
└─────────────────────────────────────────────┘
```

移动端堆叠顺序：**字符画 → 日志 → 菜单/动作 → 属性/状态 → 留言（占位）**。

> 你反馈日志是核心（"日志是重要信息，它才是丰富充实游戏的核心"），已调整为紧跟字符画之后，优先级高于属性/状态——这也和 §5 的扩展点一致：日志将来是要接跨访客数据的地方，值得放在更显眼的位置。

## 5. 状态设计（localStorage）
由于是纯静态站点，所有游戏状态默认是 **单浏览器本地** 的（换设备/清缓存即重置），这点需要和你确认是否可接受（见待确认问题 #3）。

```js
// key: "fenguan_state_v1"
{
  version: 1,
  visits: 0,          // 累计访问次数
  hunger: 60,         // 饱食度 0-100
  mood: 60,           // 心情 0-100
  tickets: 0,          // 粉票（虚拟货币，用于点单）
  ordersCount: 0,
  slurpCount: 0,
  log: [],             // 最近 N 条事件描述，环形缓冲（比如最多 20 条）
  lastVisit: "2026-09-03T00:00:00Z"
}
```

### 扩展点：日志产出要为未来的"跨访客"留口子
v1 确认只做自己的操作日志，但你要求预留以后接共享数据的能力。做法是**不要在点单/嗦粉的按钮回调里直接 `state.log.push(...)`**，而是统一走一个小的事件记录函数：

```js
function recordEvent(type, text) {
  appendLocalLog(text);      // v1：写本地 log 数组，立刻渲染
  // 未来如果接了后端，这里加一行 postToBackend(type, text) 即可，
  // 调用点（点单/嗦粉的处理逻辑）完全不用改
}
```

这样以后要做"其他访客也在…"，只需要在 `recordEvent` 里加一次上报、在渲染时把本地日志和拉取回来的共享日志合并展示，不需要重构点单/嗦粉的业务逻辑。**这次不实现上报和拉取，只保证这一层抽象存在。**

## 6. 行为设计

### 点单
- 菜单配置化：`data/fenguan/menu.yaml` 里每个米粉品类是一条记录：`name`（品类名）、`cost`（花费粉票）、`hunger`/`mood`（效果增量）、`flavorTexts`（一组随机上桌文案）。改菜单/文案只改这个 yaml。
- v1 的具体品类和文案由 AI 先占位生成（比如牛肉粉/酸辣粉/螺丝粉/桂林米粉…配对应文案），最终基调你确认后再迭代，不阻塞开发。
- 点击 → 校验粉票是否足够（不够则提示"钱包干瘪，先去嗦粉攒点人气"）→ 扣费、更新属性、通过 `recordEvent()` 追加一条随机文案到日志。
- 建议加短冷却（如按钮 disable 2-3 秒模拟"上桌中"），防止连点把玩法秒变刷分器。

### 嗦粉
- 主要的"资源产出"动作（类似 A Dark Room 的砍柴）：点击一次，粉票 +少量，饱食度略降（吃得辛苦）、心情 +少量，日志追加一条随机趣味描述。
- 建议边际收益递减或轻微冷却，避免无脑连点导致玩法失去意义。

### 留言（v1 只做占位，不接后端）
你确认这次先只放按钮，不实现存储/展示，把精力放在点单/嗦粉上。v1 做法：
- 一个「留言」按钮，点击后弹出/展示一行"敬请期待"提示，不产生任何网络请求或本地存储。
- 按钮要明确带"未开放"的视觉标记（比如置灰或加一个小徽标），不要让访客以为点了没反应是 bug。
- 真正的存储/展示方案留在下面的 Backlog，等这次的核心玩法跑通、你想做的时候再拉出来单独评审。

## 7. ASCII 美术与可访问性
- 美术方向已确认：**街边小巷子里的粉馆**——窄巷、招牌歪歪斜斜挂着、门口一张矮桌、可以加一盏灯笼/一缕蒸汽，氛围偏市井、烟火气，不是宽敞明亮的临街商铺。
- 先做一版简化占位（巷子轮廓 + 招牌 + 桌子 + 老板简笔画），跑通交互后再迭代美术细节，避免"轻量彩蛋"变成美术黑洞。
- `<pre>` 字符画在窄屏可能错位换行，需要 `overflow-x: auto` 或针对小屏切换更紧凑的画；同时加 `aria-hidden` + 文字性摘要，避免屏幕阅读器读一堆无意义符号。
- 颜色走 `--color-text` / `--color-accent`，需要分别在亮/暗主题下检查对比度和错位（暗色模式下这个"巷子"氛围可能更贴切，可以重点先看暗色效果）。

## 8. 实施步骤（建议顺序，v1 范围）
1. 菜单入口 + 空页面骨架（S）
2. 三栏静态布局 + 小巷子 ASCII 占位 + 主题变量适配（M）
3. `data/fenguan/menu.yaml` 菜单配置 + AI 占位文案/品类（S）
4. 状态机 + `localStorage` 持久化 + `recordEvent()` 抽象 + 点单/嗦粉交互（M）
5. 留言占位按钮（"敬请期待"）（XS）
6. 移动端适配（日志优先于属性/状态）+ a11y 检查 + 文案/美术打磨（S）

## 9. 风险
- 文案和字符画的工作量容易被低估——"轻量"很容易在细节打磨阶段变重，尤其 AI 占位内容和你想要的"小巷子烟火气"基调可能需要几轮迭代才能对上。
- 留言按钮只是占位，如果视觉上不做"未开放"标记，容易被当成 bug。
- `recordEvent()` 的抽象是给未来扩展留的口子，v1 阶段不要过度设计（比如不需要真的定义好后端协议），够用即可，等真做共享功能时再具体化。

## 10. 决策记录（原待确认问题，已回复）
1. **实时信息展示**：v1 只做自己的操作日志，但通过 `recordEvent()` 抽象预留跨访客扩展能力（§5）。
2. **留言墙**：v1 只做占位按钮，不接 giscus 或任何后端；giscus 方案作为 Backlog 保留，等你想做的时候再启动。
3. **状态持久化范围**：接受纯本地 `localStorage`，换浏览器/清缓存即重置。
4. **菜单内容**：走配置化（`data/fenguan/menu.yaml`），v1 具体品类/文案由 AI 先占位生成，基调后续你再定调迭代。
5. **ASCII 美术方向**：街边小巷子里的粉馆，市井烟火气，先出简化占位版本。

## 11. Backlog（本次不做，先记录候选方案）
### 留言墙的最终形态
| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A. 复用 giscus** | 新开一个 GitHub Discussions category（如"粉馆留言"），`mapping="specific"` 固定 term，嵌入方式和现有评论一致 | 零新基建、零维护成本，和站点现有评论体系风格统一 | 留言需要 GitHub 登录；iframe 默认样式，很难做出"留言墙"的沉浸感 |
| B. 引入轻量第三方后端 | 如 Cloudflare Worker + KV，或直接用 GitHub Discussions GraphQL API 拉取展示、但走自定义 UI 提交 | 体验完全可控，能做出真正的"墙" | 需要新服务/API key/一点运维，不再"轻量" |
| C. 纯本地留言 | 只存 `localStorage`，仅自己可见 | 最省事 | 违背"集中展示给别人看"的诉求，不推荐 |

推荐顺序仍是 A → B：A 现有基建直接复用成本最低，B 留给"A 的沉浸感不够"时再上。

### 跨访客共享的实时信息
如果以后想做"当前有 N 位客人""刚刚有人点了 xx"，需要一个能接收/广播事件的最小后端（同样可以先复用 giscus 的 Discussion 作为极简事件源，或者上一个小型 KV 服务）。届时 `recordEvent()` 这一层抽象已经存在，改动集中在这一个函数和渲染合并逻辑，不涉及点单/嗦粉的业务代码。

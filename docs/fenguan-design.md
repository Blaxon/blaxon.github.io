# PRD：电子粉馆（/fenguan/）

- **状态**：已上线（v1 → v2 → v3，见 §11 变更记录）
- **负责人**：hang.xiang
- **最近更新**：2026-09-05

## 1. 概述

在博客里加一个轻量互动彩蛋页——「粉馆」，玩法参考 [A Dark Room](https://adarkroom.doublespeakgames.com/)：极简文字界面，靠点击驱动一个小型状态机（资源、属性、日志），营造"深夜街边米粉馆"的沉浸感。这是一个"轻"彩蛋，不是新产品线，工作量需可控。

## 2. 目标与非目标

### 2.1 目标
- 访客能在一个页面里完成 **点单 / 嗦粉 / 留言** 三种核心动作，每次动作有文字反馈。
- 视觉上延续站点主题（minimal-black），Header/Footer 不变，只有 Body 是新玩法。
- 日志/状态的产生方式留出扩展点，方便以后接后端做成跨访客共享（见 §6.3）。

### 2.2 非目标（v1 不做）
- 不做真正的多人实时同步（比如"当前有几位客人在馆里"这种跨访客共享的实时状态）。
- 不做留言墙的实际存储/展示——只放一个「留言」占位按钮，点了之后提示"敬请期待"，不接入任何后端或 giscus。
- 不做账号系统、不做真实支付/订单。
- 不追求跨设备/跨浏览器状态同步（纯本地 `localStorage`，换浏览器/清缓存即重置）。

## 3. 用户与场景

访客是博客的普通读者，从站点导航点进「粉馆」，预期是花一两分钟随手点点、看点有趣文案的轻松彩蛋，而不是需要学习规则的"游戏"。因此交互门槛要低（无需教程）、反馈要即时（每次点击都有文字/动效反馈）、状态要能"攒出感觉"（饱腹值、心情、来访次数会随时间和操作变化）。

## 4. 现状与约束（决定技术方案的关键事实）
- 站点是 Hugo 静态站（GitHub Pages 托管），`theme = "minimal-black"`，主题以 **git submodule** 引入（`themes/minimal-black`），不改主题源码，站点自己的 `layouts/`、`static/js/`、`data/` 是项目级覆盖/新增的位置。
- Header 导航完全由 `hugo.toml` 的 `[[menu.main]]` 驱动，加入口不需要改模板，只需加一条 menu 配置。
- 主题通过 CSS 变量（`--color-bg`、`--color-surface`、`--color-text`、`--color-text-muted`、`--color-border`、`--color-accent`）支持亮/暗色，新页面需接入这套变量才能跟随全站主题切换。
- 现有 JS（`main.js`）的写法是无依赖 IIFE + `localStorage`（`try/catch` 包裹，防止隐私模式报错），新功能延续这个风格，不引入框架。
- 没有服务端、没有构建期定时任务，任何"实时"能力（天气等）只能靠浏览器端直接发请求；不引入需要 API key 的服务，避免 key 暴露在前端。
- 站点目前唯一的"跨访客共享持久化"能力是 **giscus**（基于 GitHub Discussions），用于博客评论，是唯一现成的、免费、零维护的"后端"。

## 5. 入口设计

在 `hugo.toml` 的 `[menu]` 里加一项（`pageRef`/`url` 指向 `/fenguan/`），不改 `header.html`，桌面/移动导航自动带上新入口。

## 6. 功能需求

### 6.1 页面结构

新增页面独立走专属 layout（`layouts/_default/fenguan.html`），不复用文章排版（`single.html`）。Body 结构：

```
┌───────────────┬───────────────┬──────────────┐
│ 左：实时日志    │ 中：菜单（上）  │  右：属性/状态  │
│ （最近事件流）  │    动作（下）  │ （饱腹值/心情/  │
│                │                │  来访次数…）    │
├───────────────┴───────────────┴──────────────┤
│                留言（占位按钮）                 │
└─────────────────────────────────────────────┘
```

移动端堆叠顺序：**日志 → 菜单/动作 → 属性/状态 → 留言（占位）**。日志优先级高于属性/状态，因为日志是未来接跨访客数据的扩展点（§6.3），值得放在更显眼的位置。

> 曾在页面顶部放过一版 ASCII 字符画占位（巷子轮廓 + 招牌 + 桌子），因占屏比例过大已移除（见 §11 v2）。若想找回视觉氛围，优先考虑更轻量的方式（小图标/emoji），并注意窄屏换行和屏幕阅读器可访问性（`aria-hidden` + 文字摘要）。

**验收标准**
- 页面在亮/暗色主题下视觉一致，无需额外配置。
- 三栏布局在移动端正确堆叠为单列，顺序符合上面的定义。

### 6.2 点单
- 菜单配置化：`data/fenguan/menu.yaml` 每个米粉品类一条记录：`id`、`name`（品类名）、`mood`（点单时的心情增量）、`flavorTexts`（上桌随机文案）、`slurpTexts`（嗦粉时随机文案）。改菜单/文案只改这个 yaml，不动代码。
- v3 当前菜单：红烧牛肉粉 / 麻辣牛肉粉 / 牛骨头粉 / 肉丝炒码粉，各配 3 条上桌文案 + 3 条嗦粉文案；某品类缺 `slurpTexts`，或碗里的品类在当前菜单里已找不到时，退回一组通用兜底文案。
- 点单不检查/消耗任何货币，唯一门槛是饱腹值：饱腹值 ≥ 95（"还不饱"）时点单被拦截，通过统一的事件记录函数把提示（"你还不饿，先逛逛再嗦粉吧"）追加进日志框，和其他事件文案保持一致的展示位置，而不是单独的提示行。
- 饱腹值 < 95 时可点单：点击菜单按钮后，按钮内出现一个 2 秒的动态进度填充特效（模拟"上桌中"，同时防连点），填满后获得"一碗米粉"（可嗦 3 次），并追加一条随机上桌文案到日志。再次点单会直接替换手里的碗（哪怕上一碗还没嗦完）。

**验收标准**
- 饱腹值 ≥ 95 时点击任意菜单按钮不产生新碗，日志追加对应提示。
- 饱腹值 < 95 时点击菜单按钮：2 秒填充特效期间所有菜单按钮禁用；特效结束后获得对应品类的碗（`remaining = 3`），日志追加对应品类的随机上桌文案。

### 6.3 嗦粉
- 前提是手里有碗（`remaining > 0`），没有则提示"碗已经空了，先点一碗新的粉吧"。
- 每次嗦粉：`remaining -1`、饱腹值 `+10`（上限 100）、心情 `+4`；日志追加一条该碗品类对应的随机 `slurpTexts`（找不到则用通用兜底文案）；`remaining` 减到 0 时碗清空。
- 饱腹值同时随停留时间自然衰减（每 10 秒 -1），所以嗦粉本质是"跑得比饿得快"，需要不停点单/嗦粉才能维持高饱腹值。
- 冷却 1 秒（防连点），和点单按钮一样用按钮内的动态进度填充特效展示冷却进度，而不是单纯 disable。

**验收标准**
- 无碗时点击嗦粉按钮不改变任何状态，只出现提示。
- 有碗时每次嗦粉后饱腹值、心情、日志按上述规则更新；冷却期间嗦粉按钮不可再次触发。

#### 扩展点：日志产出要为未来"跨访客共享"留口子
不在点单/嗦粉的按钮回调里直接操作日志数组，而是统一走一个 `recordEvent(text)` 记录函数：v1/v2/v3 里它只写本地 `state.log` 并触发渲染；未来如果接了后端，只需在这一个函数里加一次上报，调用点（点单/嗦粉的处理逻辑）完全不用改。这次不实现上报和拉取，只保证这一层抽象存在，且不做过度设计（不需要预先定义后端协议）。

### 6.4 留言（v1 起只做占位，不接后端）
- 一个「留言」按钮，明确带"未开放"的视觉标记（灰底徽标"（敬请期待）"），点击后在提示区展示"留言板还在装修，敬请期待"，不产生任何网络请求或本地存储。
- 真正的存储/展示方案留在 §12 Backlog，等核心玩法稳定、有需要时再单独评审。

**验收标准**
- 按钮常态即带"未开放"视觉标记，不依赖点击后才让访客知道功能未开放。

### 6.5 天气驱动的 subtitle（v2/v3 新增）
给 subtitle 加了"结合实时天气 + 时段描述粉馆氛围"的能力，动态替换 `content/fenguan.md` 里写死的默认文案，不提具体地名（文案只是巷子/天气/时段的氛围描述）；固定文案和天气动态文案分两行展示，互不覆盖。

- 数据源用 [Open-Meteo](https://open-meteo.com/)：免费、不需要注册/API key、原生支持 CORS，请求地址固定写死一组经纬度（不做浏览器地理定位，不弹权限请求，不暴露访客真实位置）。
- 文案由三段拼接：**[时段] + [天气] + [气温]**（气温只在极端时追加）。
  - 时段：按巷子所在地当地小时分 7 段（凌晨/拂晓/上午/晌午/下午/傍晚/夜里），每段配 3 条文案，覆盖 0-23 点不重叠；小时数取自 Open-Meteo 返回的 `current.time`（已按 `timezone=Asia/Shanghai` 对齐当地时间），不用访客设备时间。
  - 天气：[WMO 天气码](https://open-meteo.com/en/docs)分成 `clear`/`cloudy`/`fog`/`drizzle`/`rain`/`snow`/`thunderstorm` 七类，每类配 2 条巷子氛围文案。
  - 气温：≤5℃ 或 ≥32℃ 时追加一句"天冷/天热"的小尾巴，正常温度不加这一段。
- 用 `localStorage`（`fenguan_weather_v2`）缓存天气结果 45 分钟，避免每次访问都请求。
- `fetch` 用 `AbortController` 加 5 秒超时；请求失败、超时、`fetch` 不存在（老浏览器/隐私模式拦截）都静默吞掉，页面保留服务端渲染好的默认 subtitle（`content/fenguan.md` frontmatter 里的 `subtitle`），不影响点单/嗦粉等核心玩法。
- 请求/命中缓存成功后，把动态 subtitle 那一行文本替换掉，用和日志新增条目一致的 `opacity 0 → 1` 400ms 过渡淡入。
- 全程不判断白天/黑夜（`is_day`）：粉馆设定本身是"深夜巷子"，天气文案不区分昼夜（时段文案已经承担了这部分表达）。

**验收标准**
- 正常网络下，页面加载后短时间内 subtitle 第二行被替换为"时段+天气(+气温)"文案，第一行固定文案保持不变。
- 断网/请求失败/超时场景下，页面仍完整可用，subtitle 第二行保持空白或不出现，不报错、不影响点单/嗦粉。

## 7. 数据与状态设计（localStorage）

纯静态站点，游戏状态默认是**单浏览器本地**（换设备/清缓存即重置）。

```js
// key: "fenguan_state_v1"，version 字段当前为 2（旧版本数据直接判过期、重置为默认值）
{
  version: 2,
  visits: 0,          // 累计访问次数
  satiety: 100,       // 饱腹值 0-100，首次访问默认满值
  mood: 60,           // 心情 0-100
  bowl: null,         // 手里还没嗦完的一碗粉：{ itemId, name, remaining } | null
  ordersCount: 0,
  slurpCount: 0,
  log: [],            // 最近事件描述，环形缓冲，最多 20 条
  lastVisit: "2026-09-03T00:00:00Z"
}
```

天气缓存单独存一个 key（`fenguan_weather_v2`：`{ code, temp, hour, fetchedAt }`），与游戏状态互不影响，过期策略同样是"版本不匹配就重置"，不做迁移。

## 8. 非功能需求
- **主题一致性**：所有新增 CSS 复用主题 CSS 变量，亮/暗色自动适配。
- **无后端/零密钥**：不引入任何需要服务端或 API key 的依赖；唯一的外部请求（天气）是免 key、支持 CORS 的公共 API。
- **容错**：任何非核心功能（天气 subtitle）失败都必须静默降级，不能影响点单/嗦粉等核心玩法，也不能抛出未捕获异常。
- **隐私**：不做浏览器地理定位，不弹权限请求，不上报/暴露访客位置或设备信息。
- **可访问性**：后续补充 ASCII/图标类视觉元素时需要考虑窄屏与屏幕阅读器（`aria-hidden` + 文字摘要）。

## 9. 风险
- 文案工作量容易被低估——"轻量"很容易在细节打磨阶段变重，AI 占位内容和"小巷子烟火气"基调可能需要几轮迭代才能对上。
- 留言按钮只是占位，如果视觉上不做"未开放"标记，容易被当成 bug。
- `recordEvent()` 的抽象是给未来扩展留的口子，现阶段不要过度设计，够用即可，等真做共享功能时再具体化。

## 10. 决策记录
1. **实时信息展示**：只做自己的操作日志，通过 `recordEvent()` 抽象预留跨访客扩展能力（§6.3）。
2. **留言墙**：只做占位按钮，不接 giscus 或任何后端；giscus 方案作为 Backlog 保留。
3. **状态持久化范围**：接受纯本地 `localStorage`，换浏览器/清缓存即重置。
4. **菜单内容**：走配置化（`data/fenguan/menu.yaml`），具体品类/文案由 AI 先占位生成，基调后续迭代确认。
5. **ASCII 美术方向**：街边小巷子里的粉馆，市井烟火气；v2 决定移除，占屏比例过大不划算。
6. **天气 subtitle**：不做地理定位、不接需要 key 的服务，固定经纬度 + Open-Meteo，失败静默降级。

## 11. 变更记录

### v1（初版落地）
1. 菜单入口 + 空页面骨架。
2. 三栏静态布局 + 顶部 ASCII 字符画占位 + 主题变量适配。
3. `data/fenguan/menu.yaml` 菜单配置 + AI 占位文案/品类。
4. 状态机 + `localStorage` 持久化 + `recordEvent()` 抽象 + 点单/嗦粉交互（粉票机制、饱食度随嗦粉扣减）。
5. 留言占位按钮。
6. 移动端适配 + a11y 检查 + 文案/美术打磨。

### v2（v1 跑通后的调整）
核心动机：字符画占地太大 + 粉票这层货币没必要，饱腹值本身就够驱动玩法。
1. **移除顶部 ASCII 字符画**，页面直接从三栏布局开始。
2. **饱食度 → 饱腹值，逻辑重做**：首次访问默认 100；每 10 秒自然衰减 1 点；≥95 视为"还不饿"并拦截点单；一碗粉可嗦 3 次，每次固定 +10（封顶 100），不再像 v1 那样嗦粉反而扣饱食度。
3. **移除粉票**：点单不再检查/扣除任何货币，`menu.yaml` 里的 `cost`/`hunger` 字段去掉，只保留 `mood` 和 `flavorTexts`。
4. **日志条数上限调整为 20**，日志框高度同步加高，露出更多条目。
5. **嗦粉按钮补上和点单一致的冷却体验**（1 秒，按钮内动态进度填充特效）。
6. **日志框改为固定高度、禁止滚动**（`overflow: hidden`）。
7. **日志淡出效果改为参考 A Dark Room 的 `notifyGradient`**：固定高度 + 整框渐变蒙版覆盖整个日志框（`inset: 0`），从第 1 条到最后一条连续淡出，取代此前"最后 2 条改文字颜色"或"底部固定一条带"的做法；新日志改由单条插入 + 500ms 淡入，超出上限的旧条目直接从 DOM 移除，而非整份重画。
8. **新增天气驱动 subtitle**：接入 Open-Meteo，按天气码渲染巷子氛围文案，45 分钟本地缓存，失败静默保留默认文案（详见 §6.5）。

因 state 结构变化较大（去掉 `tickets`，新增 `bowl`，`hunger` 改名 `satiety`），`localStorage` 的 `version` 字段从 1 升到 2，旧数据直接判过期重置，不做迁移。

### v3（菜单与天气文案深化）
1. **菜单换成四款**：红烧牛肉粉 / 麻辣牛肉粉 / 牛骨头粉 / 肉丝炒码粉，每款补上专属 `slurpTexts`；嗦粉时按手里碗的品类挑对应文案，找不到再退回通用兜底文案。
2. **天气 subtitle 从单句扩展成三段拼接**：新增按当地小时分桶的 7 段时段文案，与天气、气温分句组合（详见 §6.5）；天气缓存 key 升级为 `fenguan_weather_v2`（新增 `hour` 字段）。
3. **subtitle 固定文案和天气动态文案分两行展示**，互不覆盖。
4. **去掉日志区标题和动作区常驻提示行**，界面更简洁（提示改为直接写入日志流或临时提示区）。

## 12. Backlog（候选方案，暂不实施）

### 12.1 留言墙的最终形态
| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A. 复用 giscus** | 新开一个 GitHub Discussions category（如"粉馆留言"），`mapping="specific"` 固定 term，嵌入方式和现有评论一致 | 零新基建、零维护成本，和站点现有评论体系风格统一 | 留言需要 GitHub 登录；iframe 默认样式，很难做出"留言墙"的沉浸感 |
| B. 引入轻量第三方后端 | 如 Cloudflare Worker + KV，或直接用 GitHub Discussions GraphQL API 拉取展示、但走自定义 UI 提交 | 体验完全可控，能做出真正的"墙" | 需要新服务/API key/一点运维，不再"轻量" |
| C. 纯本地留言 | 只存 `localStorage`，仅自己可见 | 最省事 | 违背"集中展示给别人看"的诉求，不推荐 |

推荐顺序仍是 A → B：A 现有基建直接复用成本最低，B 留给"A 的沉浸感不够"时再上。

### 12.2 跨访客共享的实时信息
